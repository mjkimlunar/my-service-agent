## 설계 결정 요약

**도구를 넷만 둔 이유.** 읽기 셋(재고·주문·정책)과 쓰기 하나로 나눴다. 넷째가 있어야 승인 경계를 설계할 대상이 생기고, 그 이상은 늘리지 않았다 — 도구 남발은 비슷한 이름 사이에서 잘못 고르게 만들고, 실측에서 도구 하나가 이미 190~400토큰을 차지했다. 경계는 질문의 형태로 가른다: 주문번호가 있으면 주문 조회, 없으면 재고 또는 정책.

**권한을 나눈 기준.** 상태를 **읽는** 도구와 **바꾸는** 도구를 분리하고, 쓰기는 기본 권한에서 뺐다. `request_return`은 접수 요청만 만들고 확정하지 않는다. 스키마에 제약을 적어도 그것은 안내일 뿐이므로, 실제 제한은 서버가 호출자 신원·주문 소유·현재 상태를 검사할 때 생기도록 설계했다. 환불·정책 예외·타인 정보 열람은 챗봇이 단독으로 결정하지 않는다.

**실패 뒤 행동을 그렇게 정한 근거.** 실측에서 모델은 정보가 없을 때 **묻지 않고 지어냈다**. 사용자가 창고를 지정하지 않자 임의로 한 곳을 골라 그 재고를 사실로 답했다. 그래서 모든 오류 코드에 "추정하지 않고 무엇을 묻는다"를 명시했고, 재시도는 1회로 제한한 뒤 중단·이관하게 했다. 같은 오류 2회 반복은 이관 조건이다.

## 실행하지 않은 것과 이유

**구현 전체를 하지 않았다.** 과제 범위가 설계 문서다. 도구는 `get_inventory` 하나만 계약 코드와 실행 기록을 만들어 검증했고([`my-agent/build_tool.py`](my-agent/build_tool.py), [`lab2_matrix.py`](my-agent/lab2_matrix.py)), 나머지 셋은 정의서까지만 썼다.

**RAG(`search_policy`)를 붙이지 않았다.** Qdrant MCP 연결까지는 경로를 확인했으나, 기본 임베딩 모델이 영어용이라 한국어 정책 문서에서 검색 품질을 신뢰할 수 없다. 다국어 임베딩으로 바꾼 뒤 검색 결과의 정확성을 재고 나서 붙이는 것이 맞다고 판단했다.

**오류 경로 두 개를 검증하지 못했다.** `INVALID_SKU`와 `TEMPORARY_UNAVAILABLE`은 실행 9회 동안 한 번도 발생하지 않았다. 계약에는 있으나 실측 근거가 없는 상태다.

### 다음에 측정할 지점

1. **오류를 강제 주입**해 실패 처리 규칙이 실제로 작동하는지 확인 — 계약에 적힌 대로 추정 없이 멈추는가
2. **허용 밖 대상의 조용한 정규화** — "부품 3번 창고"를 임의로 승인 창고로 바꾸는 실패는 도구 설명으로 막지 못했다. 시스템 지시로 막히는지, 입력 정규화 코드가 필요한지 전후 비교
3. **도구 4개일 때의 입력 토큰** — 1개일 때 190~400토큰이었다. 넷으로 늘렸을 때의 증가분과 그것이 선택 정확도에 미치는 영향

## 실측 요약

도구 하나(`get_inventory`)에 **설명 문장만 바꿔 9회** 실행했다. 스키마·반환·실패 규칙·문항·모델·온도는 고정했다.

| 설명 | 창고 미지정 | 허용 밖 창고 | 입력 토큰 |
|---|---|---|---|
| `minimal` | 창고를 **지어냄** | **조용히 바꿔치기** | ~187 |
| `contextual` | 창고를 **지어냄** | **조용히 바꿔치기** | ~333 |
| `contextual_v2` | **되물음** ✓ | **조용히 바꿔치기** | ~394 |

- **설명 두 문장(+61토큰)이 "지어내기"를 "되묻기"로 바꿨다.** 다만 모델은 여전히 되묻지 않고 호출을 시도했고, 실제로 막은 것은 **하네스의 인자 검사**였다. 계약 문장과 하네스 검사가 함께 작동한 결과다.
- **설명으로 못 막는 실패가 있다.** "임의로 바꾸지 말라"고 명시했는데도 존재하지 않는 창고를 승인 창고로 매핑했다. 하네스도 막지 못한다 — 그 값은 허용값이라 검사를 통과한다.
